2026-09-28 / 判断 / life-editor

見た目の見直しは、測る道具・採点する道具・案を出す道具を分けて使います

Briefing と Work のデザインを一新するときは、今の画面を数値で測り、決めた基準で採点し、そのうえで Claude Design に案を出させます。Claude Design だけに良し悪しの判断を任せると、7 月の作業と同じ手戻りが起きます。

  • 今日から

    実ブラウザの計測と、目で読む確認

    Playwright で画面を撮り、アイコンの数や大きさ、余白とアニメーションの値を DOM から数えます。スクリーンショットは Claude が切り抜いて拡大し、自分で読みます。

  • 今日から

    採点表と、値の段階を先に決める

    余白・アイコンの大きさ・アニメーションの長さに決まった段階がまだありません。先に段階を決めておかないと、直しても値の直書きが増えるだけになります。

  • 今日から

    Claude Design で案を 2〜3 個出す

    リポジトリから配色と部品を読み込ませれば、今のアプリに沿った案を出せます。ただし、案の良し悪しは採点表で判断します。

  • 必要になったら

    このチャットの中のデザインキャンバス

    アイコン 1 個の要否や余白の詰め方のような小さな比較だけなら、Claude Design を開かずにこのチャットで並べて見せられます。

  • 入れない

    Figma などの外部デザインツール

    正本が 2 つになり、完成までコスト 0 円の方針にも合いません。Claude Design で足ります。

  • 入れない

    7 月の指示書をそのまま使う

    Work の指示書は旧パレット（青）のままで、今の履歴タブやフリーセッションを知りません。Briefing の指示書はそもそもありません。

たとえると料理です。計量カップで材料を量り（計測）、味見の基準を決めて味を見て（採点）、そのうえで新しい献立を考えてもらいます（案出し）。献立を考える人に味見まで任せると、「見た目は華やかでも、食べたい味ではない」皿が出てきます。

進め方

同じ計測と採点を、直す前と直した後の 2 回かけます。点数が上がったかどうかで、見た目が良くなったかを判断します。

STEP 1

前提を揃える

余白・アイコンの大きさ・アニメーションの長さの段階を決め、tokens.css に足します。古い指示書と部品集も今の色に直します。

STEP 2

今の画面を測る

Desktop と Mobile、ライトとダークの 4 通りで撮影し、アイコン・余白・アニメーションの値を一覧にします。

STEP 3

採点する

別のエージェントが採点表で点を付けます。案を作った本人に採点させないためです。

STEP 4

案を出して選ぶ

Claude Design で 2〜3 案を作り、採点と並べてこうだいさんが 1 つ選びます。

STEP 5

実装して測り直す

実装後に STEP 2 と 3 をもう一度かけ、点数の差を PR に載せます。

道具ごとの得意と苦手

道具判定得意なこと苦手なことここでの役割
Claude Design（claude.ai/design）採用リポジトリや CSS から配色と部品を読み込み、それに沿った画面案を短時間で複数出せます。2026 年 6 月から Claude Code と双方向に同期できます。7 月の作業では、空の状態とローディングの状態が作られず、使ってよい色の外の色と読み上げ用のラベルの欠落が混ざりました。外部のレビューでも「見栄えは良いが、伝わるかの判断は人が要る」と評価されています。案を出す係です。
Playwright（実ブラウザ操作）採用決まった画面幅で撮影できます。DOM から計算済みのスタイルを読み、アイコンの数、余白の値、アニメーションの長さを数えられます。「美しいか」は判定できません。9 月の画面点検も、崩れ・はみ出し・タップ寸法の確認に留まりました。測る係です。起動はメインのチャットだけにします。
スクリーンショットを切り抜いて読む手順（visual-inspect スキル）採用細かい文字やアイコンの見分けやすさを、Claude が拡大して自分で確かめられます。基準が無いと感想で終わります。採点係の目です。
採点表（新しく作るスキル）新規見る観点と点の付け方を固定し、直す前と後で同じ物差しを当てられます。まだありません。今ある UI 設計のスキルは色・状態・アクセシビリティの規約が中心で、アイコンの要否・余白のリズム・視覚の階層を判断する基準を持っていません。採点の物差しです。
このチャットのデザインキャンバス（Design 型の Artifact）保留ログインの追加なしで、小さな案の比較をすぐに並べられます。life-editor の配色と部品を登録したデザインシステムがまだありません。案の幅は Claude Design より狭くなります。小さな比較の係です。
Figma見送りピクセル単位の作り込みと、複数人での共同編集が得意です。正本が 2 つになり、コストもかかります。一人で作るこのアプリには大きすぎます。使いません。

採点表の観点（案）

こうだいさんが挙げた観点を、測れる形に直しました。点は 1〜5 で付け、数値で測れるものは数値も添えます。

観点数値で測るもの目で見て判断するもの
アイコン画面にあるアイコンの数、大きさの種類の数、文字のラベルが付いていないアイコンの数を数えます。意味が重なるアイコン、飾りだけのアイコン、何をするか見て分からないアイコンを挙げます。
余白使われている余白の値を集め、決めた段階から外れている値の数を数えます。まとまりごとに余白が揃っているか、詰まりすぎや空きすぎの場所がないかを見ます。
アニメーション動きの長さと数を集めます。UI 設計のスキルが決めている 3 つの帯（100〜150 ms / 200〜300 ms / 400〜600 ms）から外れた値と、動きを減らす設定で止まらない動きを数えます。動きが意味を持っているか、散らばった小さな動きが多すぎないかを見ます。
視覚の階層文字の大きさの種類の数を数えます。最初に目が行く場所が、その画面の一番大事な情報になっているかを見ます。
画面をまたいだ揃い方同じ部品の寸法が画面ごとにずれていないかを比べます。Briefing と Work がほかの画面と同じアプリに見えるかを見ます。

項目状態説明
値の段階不足shared/src/styles/tokens.css で決まっているのは、角丸・影・余白 2 種（8px と 12px）です。アニメーションの長さとアイコンの大きさの段階はありません。
Briefing の指示書なし.claude/docs/design/briefs/ に Briefing の指示書がありません。画面のコンセプトは #2035 で決める途中です。
Work の指示書古いbriefs/work.md は旧パレット（青 #1d4ed8）を埋め込んだままです。その後に Work のコミットが 27 本入り、履歴タブとフリーセッションが増えました。
UI 設計のスキルと部品集古いUI 設計のスキルの説明文と shared/design-system/claude-design/ の部品集は、旧パレット（コバルトとミント）のままです。
Claude Design との同期未接続同期の道具は、こうだいさんが /design-login を実行するまで使えません。life-editor のデザインシステムもまだ登録していません。
アイコンの使用数少ないBriefing は 7 種（BriefingView.tsx に 5 種など）、Work の画面本体は 2 種です。Work の多くは共通部品から来るので、実際の数は STEP 2 で数えます。

置いた仮定

  • Work を先に進めます。Briefing は画面の役割そのものを #2035 で見直す途中なので、見た目だけを先に直すと二度手間になるからです。
  • Claude Design での生成と修正の指示は、7 月と同じくこうだいさんの作業とします。Claude Code 側の準備は、指示書と部品集を今の状態に直すところまでです。
  • 値の段階（余白・アイコン・アニメーション）はコードの変更になるので、Issue にして担当の作業に回す前提です。採点表はハーネス（開発を回す仕組み）の追加なので、Issue にせず .claude/skills/ に置きます。
