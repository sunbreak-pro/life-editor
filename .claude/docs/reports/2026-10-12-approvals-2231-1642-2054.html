01#2231 集計

#2231 は、専用テーブルに設定を保存する案で承認してよいです

体重のように足し算に意味がない記録でも、いまは件数と合計しか出せません。Mobile の記録ブロックは recordsModel.ts:210、MCP の要約は recordHandlers.ts:583 で、どちらも合計と件数だけを出しています。平均（avg）を出す関数はありますが、最新（latest）を出す関数はありません（appRecordAggregation.ts:54-60）。#2231 は、この足りなさを埋める依頼です[1]。

計画書は Status が Draft のままで、PR #2233 に載っています[2]。決めることは置き場所、表示の中身、初期値の 3 点です。3 点が決まれば、9 段階の作業に分けて進められます。

置き場所の推奨は B です。Desktop と Mobile で同じ設定が見えるためです。

Desktop と Mobile の両方で同じ設定を見せられるのは、専用テーブルの B だけです
案利点欠点
B（推奨）専用テーブルDesktop と Mobile で揃います。claude 由来の種類にも置けます。0041 の DDL（テーブルを作る命令）が要ります。RLS（利用者ごとに見せる範囲を決める仕組み）と Realtime（変更を画面へすぐ届ける仕組み）も要ります。同期、書き出し、退会の処理も追随させます。db push が要ります。
A ブラウザ内の保存DDL が要りません。端末ごとに違う値になります。公開 Web URL が主導線なので、ブラウザを変えると設定が最初の状態に戻ったように見えます。
C extension_apps の JSON 列テーブルが増えません。claude 由来の種類や、台帳にない種類を置く場所がありません。

A・B・C は計画書の案の記号です。DDL・RLS・Realtime は、データベースの設定と通知の仕組みを指します。

表示の中身は、値の出し方（合計・平均・最新・件数）とグラフの形（棒・折れ線）の両方を選べるようにする案を推奨します。折れ線は新しい部品です。差分が 500 行を超えたら、グラフの形（Step 6）を別の PR に分けます。

初期値は、すべて「合計」にします。今の表示と同じになります。kg なら最新、のように値の出し方を自動で決める案は、外れる種類が必ず出るため計画書で退けています。

9 段階のうち、人の手が要るのは Step 4 と 9、目で確かめるのは Step 7 です
#StepGateAcceptance
1shared と mcp-server に記録の日時（occurredAt）と最新（latest）を足す自律同じ見本データで最新の値が一致します。同じ時刻なら id の大きいほうを選びます。
2MCP の records 要約と list_records に平均と最新を足し、道具の一覧を作り直す自律toolCatalogFreshness.test.ts が緑になります。
3記録タブと Mobile の記録ブロックに平均と最新を出す自律体重で足し算が出ないことを確かめます。
4設定テーブルの DDL、データ層、同期、書き出し、退会を作る人手db push のあと、list_tables で表と RLS を確かめます。
5種類ごとに値の出し方を選ぶ画面を作る自律未確認（計画書に条件の記載がありません）。
6グラフの形（棒・折れ線）を選べるようにする自律色は lumen-* のトークンだけで当てます。
7実ブラウザで、1440px と 390px の light と dark を確かめる目視人が画面を見て判定します。
8docs を追随させる自律docs-lint が緑になります。
9merge する人手未確認（計画書に条件の記載がありません）。

Gate は、自律が Claude の確認で進む作業、人手がこうだいさんの作業、目視が画面を見て判断する作業です。Acceptance は、その Step が終わったと言える完了の条件です。同時に進める作業の枠（レーン）は、Step 1 と 4 が refactor-core、Step 2 が mcp-tools、Step 3・5・6 が analytics-refine です。

着手の前に、次の 4 点に注意が要ります。

  • 記録 1 件の形（AppRecordPoint）が変わるため、recordsModel.ts、recordHandlers.ts、見本データの JSON も一緒に直ります。
  • 退会時にデータを消す関数（delete_my_account()）を作り直すときは、最新の 0040 の本体を元にします。元にしないと、app_records や tables_payload が消す対象から抜けます。
  • db push は merge より先に行います。後だと「データを書き出す」処理が、まだ存在しない表を読んで失敗します。0039 のときと同じ失敗です。
  • migration 番号（DB の変更ファイルの通し番号）の 0041 は未使用で、open の PR は 0 件です。着手のときに改めて確かめます。
