2026-09-20 / 判断 / life-editor

外部記憶としては筋が通る。Issue の置き換えだけが噛み合わない

life-editor を他プロジェクトの外部記憶・保管庫・分析対象にする構想は、そのまま進めて問題ありません。ただし GitHub Issue の役割を移す部分だけは、データモデルと並行作業の両方で壊れます。

  • 今日から

    記録と采配の層として置く

    「今日どれをやるか」「なぜそう決めたか」「何が起きたか」を Todo / Note / Daily に集める。GitHub に無いのは時間軸と横断の一望で、そこが life-editor の取り柄です。

  • 必要になったら

    GitHub からの一方向ミラー

    Issue を Todo に機械コピーする。状態の正本は GitHub のまま。ミラーが壊れても再生成すれば直る形に限る。

  • 入れない

    課題状態の正本を移す

    ステータスも担当も追記も無く、後勝ち同期で消える。PR とマージ判定の結線も切れます。

前提: life-editor はまだ移行中（Tauri から Electron + Capacitor + Supabase へ）で、移行 SSOT が現役です。ほかのプロジェクトが基盤として依存すると、移行中の破壊的変更がそちらの開発を止めます。

なぜ Issue の置き換えだけが噛み合わないか

GitHub は在庫棚です。何がいくつあって、いつ入って、いつ出たかを機械が正確に言える台帳。life-editor は献立表です。今日は何を作るかを決めて、作った記録を残す場所。献立表は在庫棚の上に乗ると強いのですが、在庫棚を献立表で置き換えると、賞味期限が誰にも分からなくなります。

現物を読んで確かめた噛み合わなさが、下の 6 行です。

課題追跡に要るものlife-editor実物
状態遷移（調査中 / 着手 / レビュー / 完了）なしnot_started と done の 2 値だけ（mcp-server/src/tools/todo.ts:124）
プロジェクト軸（どのリポジトリの課題か）なしitems_meta のスコープは user_id のみ。role も 5 種の CHECK 制約で固定（supabase/migrations/0008_data_unification_schema.sql:80）
コメント（追記）なしupdate_todo の content は全文置換。後から書いた側が前の内容を消す
同時書き込みの安全性なし同期が LWW（後勝ち）。別 worktree・別セッションの並行更新が無言で消える
担当・優先度・関連 PRなし単一ユーザー前提の設計なので、そもそも持っていない

とくに効くのは 3 行目と 4 行目です。GitHub の Issue が並行作業に強いのは、コメントが追記しかしないから。誰が何を書いても他人の文章は消えません。life-editor の Todo は本文を丸ごと差し替えるので、Orca で 2 レーン同時に走らせた瞬間に片方の記録が消えます。しかも後勝ち同期なので、消えたことに誰も気付きません。

役割をどう分けるか

GITHUB

事実

Issue / PR / CI / ラベル / マージ状態。機械が一意に判定できるものだけを置く。人のレビュー窓口も diff が見える GitHub が担う。

LIFE-EDITOR

文脈

今日どれをやるか、なぜそう決めたか、何が起きたか。判断台帳（Note）と作業ログ（Daily）と采配（Todo / Schedule）。

ORCA

実行

エージェントが実際に手を動かす場所。両方を参照するが、事実の書き込み先は GitHub に寄せる。

この切り方なら、life-editor は Issue の置き換えではなく Issue の上に乗る采配レイヤーになります。GitHub が持っていない「複数プロジェクトを時間軸で一望する」機能が素直に効きますし、GitHub が得意な機械的な結線も失いません。

改良点

1. ミラーは一方向に限る

GitHub Issue から life-editor Todo への片方向コピーだけにします。タイトル・URL・ラベルだけを機械生成し、life-editor 側は読み取り中心。状態を戻す経路を作らなければ、後勝ち上書きの事故は原理的に起きません。ミラーが壊れたら作り直すだけです。

2. プロジェクト軸はタグ規約で決め打つ

DDL を足さずに済ませるなら、proj/original-card-battle のような名前空間つきタグを規約にします。tag_entity は存在しないタグを自動で作るので、追加実装ゼロで始められます。Connect がタグを入口にした横断ビューなので、そのままプロジェクト別の一望になります。

3. 1 Todo = 1 書き手にする

複数のエージェントが同じ Todo の本文を更新する形にしない。複数人が書くログは Daily か専用 Note に寄せ、Todo の本文は 1 レーンだけが触ります。

4. 鍵を 1 本のまま渡さない

Remote MCP の認証は URL パスの共有シークレット 1 本で、ツール単位の権限分離がありません。他プロジェクトのエージェントにそれを渡すと、日記もスケジュールも全部同じ鍵で書き換えられる状態になります。remoteTools.ts は既に「公開面には低権限のツール集合だけを出す」という設計思想を持っているので、同じ発想で読み取り + 追記だけの開発用ツール集合を足すのが筋です。

5. 依存はアダプタ 1 枚に閉じる

他プロジェクト側は .claude/ にスキル 1 つ（既存の life-editor-note と同じ形）だけを置き、そこからしか life-editor を触らせない。life-editor が移行で壊れても、そのスキルが黙って失敗するだけで済みます。移行が終わるまでは書き込みを Note / Daily に限り、読み取りは自由にしておくのが安全です。

それでも Issue 機能を持たせたい場合

必要になる最小の変更はこれだけあります。CLAUDE.md §4 の判断基準（特化 UI が要るなら特化テーブル）で言うと、課題追跡はフィルタ・状態遷移・コメントという特化 UI が要るので、汎用の Todo に相乗りさせる形にはなりません。

-- 1. 状態を 2 値から広げる（tasks_payload.status の enum 拡張）
-- 2. プロジェクト軸の列を足す（または role に 'issue' を追加 = CHECK 制約の変更）
-- 3. 追記専用の子テーブル（item_comments）を新設
--    → これが無いと並行作業で記録が消える
-- 4. 上 3 つに対応する UI（フィルタ・状態遷移・コメント欄）

ここまでやると「特化専用アプリ」に寄っていき、Non-Goals の線に近づきます。GitHub をやめる強い理由がない限り、割に合いません。

置いた仮定

  • 組み込み先は original-card-battle のような GitHub リポジトリを持つプロジェクトで、既に .github/ を使っている。
  • Orca で複数レーンを並行させる前提（単一レーンなら後勝ち上書きの危険はかなり下がります）。
  • 「人がレビューする窓口」はコードの diff レビューではなく、AI の作業結果を人が読む窓口を指している。

未確認のこと

  • Orca 側が課題やタスクをどう保持しているか（life-editor と役割が重なる部分があるかは見ていません）。
  • Remote MCP を他プロジェクトから実際に叩いたときのレイテンシとレート制限。
  • ミラーを回す実行主体（cron / hook / 手動）をどこに置くか。

次に判断が要る点

  • 状態の正本を GitHub に残すか、life-editor に移すか。ここが決まらないと他がすべて宙に浮きます。
  • プロジェクト軸をタグ規約で済ませるか、DDL で列を足すか。
  • 移行完了を待つか、今から薄いアダプタだけ先に入れるか。
