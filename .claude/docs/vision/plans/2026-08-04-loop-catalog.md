# Plan: ループカタログ — 「縛る」から「考えさせる」への転換

> **これは何か**: 名前を指定するだけで回るループ（= 再利用可能な作業定義）のカタログを整備し、作業単位ごとの目的・完了条件・境界を宣言的に扱えるようにする設計方針書。
> **親計画との関係**: `2026-07-28-loop-engineering-harness.md` が「いつ・どのレーンを自走させるか」（時間軸）を扱うのに対し、本書は「1 本のループの中身をどう書くか」（構造）を扱う。**親計画 Phase 2（実装レーンの自走）の前提条件**として先行実施する（2026-08-04 裁定）。
> **姉妹計画**: コンテキストの常時ロード費用そのものの削減は `2026-08-04-context-cost-reduction-harness.md` が扱う。本書はコスト削減を目的に含めない。

---

## Context

### 動機

1. **ループの起動が毎回アドホック** — 作業のたびに目的・完了条件・停止条件を口頭で組み立て直しており、同じ種類の作業でも 1 回ごとに結果がぶれる。
2. **止まるべきところで止まらない / 進めるところで止まる** — 反復上限と「人間に返す条件」がループ側に宣言されていないため、判断の委譲範囲がその場の空気で決まっている。

### 設計思想（本書の前提）

モデル側の推論能力は既に十分高いため、**細則で縛るほど品質は上がらない**。したがって:

- **禁止は文章で書かず、機械で不可能にする**（hooks / permissions）
- **手順は書かず、目標・完了条件・境界だけを渡す**（ループ定義）
- **削った細則の分だけ「なぜ」を厚くする** — 判断を委ねる以上、判断基準の供給が必要

### 制約

- 移行期間中（Electron + Capacitor + Web + Supabase）。移行 SSOT と競合する記述は作らない
- merge と main への取り込みは常にユーザー（親計画 POLICY P-001。本書でも解除しない）
- $0 運用（サブスク枠内）
- 既存資産（skills / agents / hooks / comm / decisions）は作り直さず接いで使う

### Non-goals

- プロダクトコードの変更（変更範囲は `.claude/skills/loop-*/` のみ）
- CLAUDE.md の再編・常時ロード分の削減（→ 姉妹計画）
- 既存スキル群の一斉リネーム・統廃合
- 夜間自走の範囲拡大（親計画 Phase 1 の判断に従う）

## 1. ハーネス上の位置づけ

```
[常時ロード]  CLAUDE.md            事実と判断基準            ← 姉妹計画の管轄
[条件ロード]  skills/ rules/ docs/  手順・規約・経緯          ← 現状維持
[明示起動]    skills/loop-*/        ループカタログ            ← 本計画
[機械強制]    hooks/ + permissions  禁止事項の実体            ← 現状維持
```

一文で言うと、**「事実は常時・手順は条件付き・ループは明示・禁止は機械」**。本計画は 3 段目だけを扱う。

## 2. 判断軸

本計画の運用中、迷ったらこの 3 表で決める。

### 2.1 縛るか、考えさせるか

| 対象                                   | 扱い                           | 理由                           |
| -------------------------------------- | ------------------------------ | ------------------------------ |
| 不可逆操作・秘匿情報・main 保護        | **縛る**（機械強制）           | 確率的に守られては困る         |
| 環境の事実（パス・コマンド・既知の罠） | **教える**（事実として明記）   | 知らなければ推論では埋まらない |
| 設計判断・実装方針・命名・粒度         | **考えさせる**（基準だけ渡す） | 細則を書いても品質は上がらない |
| 完了の定義                             | **機械で判定させる**           | 主観で終わらせない             |

### 2.2 ループの粒度

- **1 ループ = 1 セッション = 1 目標**。またぐなら分割する
- 反復上限を必ず宣言し、超えたら成果ではなく**仮説を出して停止**する
- 停止して人間に返す条件を先に書く（要件が二義的 / スキーマ変更 / Non-Goals に触れる）

### 2.3 自動発火か、明示起動か

|                | 自動発火                   | 明示起動（`disable-model-invocation`） |
| -------------- | -------------------------- | -------------------------------------- |
| 向くもの       | 軽量・読み取り中心・補助的 | 反復を伴う・書き込む・実行時間が長い   |
| 本計画での既定 | 既存スキルは現状維持       | **ループはすべて明示起動**             |

理由: 発火タイミングが曖昧なままでは、実行時間を事前に見積もれない。**判断はモデルに委ねるが、着火は人間が握る。**

## 3. ループカタログ（初期セット）

| ループ             | 目標                                                 | 主な停止条件                      |
| ------------------ | ---------------------------------------------------- | --------------------------------- |
| `/loop-triage`     | 自分宛 open Issue が着手可能かを判定し、着手順を出す | 要件が二義的 → decision キューへ  |
| `/loop-implement`  | Issue 1 件を実装し draft PR まで持っていく           | 反復上限到達 / スキーマ変更が必要 |
| `/loop-verify`     | 変更に対する検証ゲートを通し、落ちた原因を切り分ける | 環境起因と判断した時点            |
| `/loop-postmortem` | 失敗の記録を読み、事実か skill に 1 行足す           | 追加先が判断できない時            |

各ループ定義に必須の見出しは **目標 / 完了条件（機械検証可能）/ 予算 / 停止条件 / 使ってよい道具** の 5 つ。**手順は書かない。**

`loop-postmortem` が知見を足す一方、肥大を戻す `loop-prune` は姉妹計画側で定義する（同じ `loop-*` 名前空間に加わる）。**この対が揃うまでカタログは片肺**である点に留意する。

---

## 4. 実装の進め方（2026-08-04 裁定）

本書は方針のみを持ち、**細部は実装チャット自身が実測してから決める**。

1. セッション開始時に本書を渡す
2. 実装チャットがローカルの実態を調査する
   - ユーザーレベルスキル（`~/.claude/skills/`）の役割系・パイプライン系の中身と実運用
   - 既存のリポジトリ内スキルとの責務の重なり
   - hooks / permissions が既に機械強制している範囲
3. 調査結果をもとに、**より密な子計画書**を `docs/vision/plans/` に起こす
4. その子計画書のレビューを経て実装に入る

ループは既存パイプラインを**呼び出す薄い外枠**とし、処理をループ側に寄せない（二重管理の回避）。ただし実測の結果それが成立しない場合は、子計画書で理由を添えて修正してよい。

## Risks

- **ループの増殖** — カタログが増えるほど選択と保守の負荷が上がる。棚卸しは姉妹計画の `loop-prune` に委ねる
- **外枠が厚くなる** — 既存パイプラインとの二重管理が起きると、どちらが正本か分からなくなる。責務境界を子計画書で明文化してから実装する
- **監視の緩み** — 安定して信頼が生まれた頃が最も危険（親計画 §3 の知見）。不可逆操作の人間ゲートは本計画でも恒久
