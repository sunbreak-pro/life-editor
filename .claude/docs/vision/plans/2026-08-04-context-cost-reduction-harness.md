# Plan: コンテキストコスト削減ハーネス — 測って、減らして、戻らない仕組みを作る

> **これは何か**: セッションごとに固定で乗るコンテキスト費用を実測し、削減し、**再肥大しない機構**を作るための調査 + 実装計画。
> **主目的は削減そのものではなくハーネスの構築**。一度削っても維持機構がなければ数か月で戻るため、計測・棚卸し・移送を回し続ける仕組みを最終成果物とする。
> **姉妹計画**: ループ定義の構造は `2026-08-04-loop-catalog.md` が扱う。本書はそこから分離したコスト系の全項目を引き受ける。

---

## Context

### 動機

1. **固定費が見えていない** — セッション開始時点で何がどれだけ積まれているかを誰も測っていない。CLAUDE.md だけが議論の対象になりがちだが、実際の支配項は別の可能性が高い。
2. **削減が一過性で終わる** — 「変わらない事実だけを持つ」方針で運用してきたにもかかわらず、手順・経緯・実測エピソードが再び混ざる。**方針だけでは戻る。**
3. **判断材料がない** — 何を残し何を移すかを、感覚ではなく費用対効果で決めたい。

### 仮説（調査で検証する)

- CLAUDE.md 本体よりも、**そこから参照される大型 SSOT の読み込み**の方が重い可能性がある
- **MCP サーバーのツール定義**は毎セッション積まれるため、使用頻度の低いサーバーが常時費用になっている可能性がある
- path-scoped の詳細規約は、**実際の発火頻度**次第で常時費用に近い扱いになっている可能性がある
- SessionStart hook の出力・派生 INDEX の再生成結果も、毎回コンテキストに入るなら固定費である

いずれも**未実測**。本計画の Phase 1 はこの検証だけを目的とする。

### 制約

- 移行期間中（Electron + Capacitor + Web + Supabase）。**本格的な移送は移行完了後**に行う（2026-08-04 裁定）。移行中は計測と枠づくりに留める
- 消失ゼロ — 削除は移送先の確保とセットで行う。移送先が無い記述は、移送先を作るまで消さない
- 既存ゲート（lint / build / test / docs-lint）を壊さない
- $0 運用

### Non-goals

- 削減量そのものを KPI にすること（削りすぎは探索コストを増やし逆効果）
- ループ定義の構造設計（→ 姉妹計画）
- モデル選択・思考量チューニングによる削減（本計画はコンテキスト側に限定）

## 1. ハーネスの全体像

```
[計測]   固定費を定期的に測る            ← これが無いと何も判断できない
   │
[判断軸] どこに置くべきかを表で決める    ← 感覚で決めない
   │
[移送]   常時 → 条件付き / 参照 へ移す   ← 削除ではなく移送
   │
[維持]   /loop-prune で棚卸しを回す      ← 戻らないための機構（最終成果物）
```

削減は 3 段目で起きるが、**成果物として残すのは 1 段目と 4 段目**である。

---

## 2. 判断軸

### 2.1 その記述をどこに置くか

| 性質                                   | 置き場                 | 例                                               |
| -------------------------------------- | ---------------------- | ------------------------------------------------ |
| 常に必要で、モデルが知りようがない事実 | CLAUDE.md 航法         | ディレクトリの責務・検証コマンド・踏むと壊れる罠 |
| 判断の優先順位・プロダクトの意図       | CLAUDE.md 目的         | Vision・Non-Goals・優先順位                      |
| 特定の作業をする時だけ要る手順         | skills/                | worktree 操作・DB migration・Issue 起票          |
| 特定パスを触る時だけ要る規約           | rules/（path-scoped）  | frontend 規約                                    |
| 破られたら事故になる禁止               | hooks / permissions    | main への push・トークン平文                     |
| 経緯・実測・失敗談                     | docs/ ・ known-issues/ | なぜその決定になったか                           |

判定式は **「消したら Claude が間違うか」+「毎回必要か」**。毎回必要でないなら常時ロードから外す。

### 2.2 削ってよいか

| 状態                             | 判断                           |
| -------------------------------- | ------------------------------ |
| 移送先が既にある                 | 移送して削る                   |
| 移送先が無いが作れる             | 移送先を作ってから削る         |
| 移送先が無く、作る先も決まらない | **残す**（削減を目的化しない） |
| モデルが推論で埋められる一般知識 | 削る                           |
| 環境固有の事実                   | 削らない                       |

### 2.3 常時ロードの再編（航法 / 目的の 2 層）

CLAUDE.md は最終的に次の 2 層のみを持つ形へ再編する。

- **A. 航法（Navigation）** — 探索コストを下げる「事実」だけ。構造・参照先マップ・検証コマンド・既知の罠
- **B. 目的（Why）** — 判断を委ねるための「基準」。Vision・Non-Goals・優先順位

全面書き換えではなく **既存記述の振り分け**として行う。手順は skill へ、経緯は docs へ、禁止は hooks / permissions の実体へ。実体が無い禁止は、実体を作ってから文章を削る。

## 3. Phase 構成

```
Phase 1  計測          ← 今ここ。移行中でも実施できる
  │  固定費の内訳を測り、支配項を特定する。この時点では何も削らない
  │  昇格条件: 内訳が数字で出ており、上位項目が特定できている
  ▼
Phase 2  枠づくり
  │  航法 / 目的の枠を CLAUDE.md に用意し、移送先（skill / docs）を先に作る
  │  昇格条件: 移送先が揃い、消失ゼロで移送できる状態
  ▼
Phase 3  移送          ← 移行（Electron + Supabase）完了後に実施
  │  Phase 1 の上位項目から順に移送する。1 回の PR で 1 項目
  │  昇格条件: 既存ゲートが緑・再測定で固定費が下がっている
  ▼
Phase 4  維持機構
     /loop-prune を定義し、定期的な棚卸しを回す。カタログ自身も対象に含める
```

## 4. Phase 1 の調査項目

**何も削らず、内訳を出すことだけを目的とする。**

| 対象                      | 見るもの                                                             |
| ------------------------- | -------------------------------------------------------------------- |
| CLAUDE.md                 | 実サイズと、そこから参照されるファイルの追跡実態                     |
| 大型 SSOT（移行 SSOT 等） | 実際に何回・どの範囲まで読まれているか                               |
| MCP サーバー              | 接続中サーバーのツール定義がセッション開始時に占める量と、実使用頻度 |
| path-scoped rules         | 発火条件と実際の発火率                                               |
| SessionStart hook         | 出力がコンテキストに入るか、入るなら量                               |
| skills の説明文           | 全 skill の説明文が常時読まれる前提での合計量                        |
| memory / history          | セッション開始時に読まれる範囲                                       |

調査結果は本書の Worklog ではなく、**独立した計測結果ファイルに残す**（再測定して差分を見るため）。

## 確定事項（2026-08-04 裁定）

- **計測は二段構え** — まず概算で上位項目だけを特定し、そこだけ精密に測る。全項目の精密計測はしない（調査自体のコストを抑えるため）
- **削減の数値目標は置かない** — 基準は「移送先があるものは移す」のみ。固定費の上限値を運用ルールにしない（削りすぎの防止）
- **大型 SSOT の分割可否は Phase 1 の結果を見てから決める** — 移行中の分割は事故りやすいため、先に方針を固定しない

---

## Risks

- **削りすぎ** — 「モデルは分かるはず」で環境固有の事実まで削ると、探索が増えて逆に高くつく。2.2 の判定表を必ず通す
- **移行との衝突** — 移行中に移送すると、移送先自体が動く。Phase 3 を移行完了まで開始しない
- **調査が目的化する** — 計測に時間をかけすぎない。上位項目が見えた時点で次へ進む
- **維持機構の未完** — Phase 4 まで到達しないと、削減は数か月で元に戻る。**Phase 3 単独での完了扱いを禁止する**
