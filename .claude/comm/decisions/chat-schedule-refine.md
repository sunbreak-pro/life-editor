## D-20260730-sched-1: 編集パネルで日付を変えたとき、カレンダーを移動先の日へ飛ばすか

**背景**: #469 で編集パネルに日付ピッカーを付けた。日付を変えると、その行は今表示している週から外れて見えなくなる。

**A（採用・現行実装）: 飛ばさない**。カレンダーは今の週のまま。エディタは開いたままで、日付欄が新しい日を表示する。行がグリッドから消えるのは次の同期後。

- 利点: 壊れない。飛ばす実装（#484 初版）は、可視範囲が変わると再フェッチが `rangeItems` を置き換えて**保存が着地する前の楽観更新を捨てる**ため、行がどこにも無い瞬間に詳細パネルが自分で閉じた（QA の Blocking B-2）
- 欠点: 移動先を目で確認できない（日付欄の数字で確認するしかない）

**B: 飛ばす（保存の着地を待ってから）**。`updateScheduleItem` を await 可能にして、DB に着いてから anchor を動かす。

- 利点: 移動先が見える
- 欠点: `useScheduleItemsAPI` の書き込み API を await 可能にする改修が必要（現状 void の fire-and-forget）。失敗時の toast 設計も必要

**放置時**: A のまま（安全側）。移動先を見たい要望が出たら B を Issue 化して実装する。

## D-20260731-sched-2: #468 の台帳フィルタに「予定へタグを付ける導線」を同梱するか

**背景**: #468 でカレンダー台帳をグリッドのフィルタとして配線する。ところが実測したところ、**アプリ内に予定（event）へ life-tag を付ける導線が存在しない**（`assignTagToItem` の呼び出し元は Notes 詳細とタスク Kanban の TagPicker だけ・Schedule のコンテキストメニューの「タグを追加」は stub）。このままフィルタだけ入れると、カレンダーを選んだ瞬間に予定が全部消えてタスクチップだけ残る。

**A（採用・既定）: 同梱する**。編集パネル（`EventEditorPane`）に `tagSlot` prop を 1 本足し、既存 `TagPicker` を注入するだけの最小追加。繰り返し由来の行は `routineId` を対象にして系列単位で付ける。

- 欠点: #468 の差分が編集パネルにも伸びる（#467 の Mobile 領域とは別ブランチなので衝突はしない見込み）

**B: フィルタだけ先に出す**。予定のタグ導線は別 Issue に切る。

- 利点: 差分が shared/utils + Desktop ツールバー + 台帳モーダルに閉じる
- 欠点: 台帳フィルタが実質タスク専用のまま出る。「配線したのに効かない」が 1 PR 続く

**放置時**: A で実装して PR を出す（フィルタが機能する状態で着地させるのが安全側。B に倒す場合はタスク 7 を落とすだけで済む）。

## D-20260801-sched-2: Connect グラフのダブルクリックを「開く」に返すか、d3 の拡大のまま残すか

**背景**: #524 の実装中に実測。ノードのダブルクリックは `onActivate`（アイテムを開く）を一度も呼んでいない。`d3-zoom` が canvas に登録する `dblclick.zoom` が `stopImmediatePropagation()` を撃ち、後から登録している自前の dblclick リスナーへ届かないため。今そこで起きているのは **d3 既定のダブルクリック拡大**。#523 / #524 の退行ではなく最初からこの形で、「開く」導線自体は選択カードのボタンが生きている。

**A（推奨）: ダブルクリックを「開く」に返す**。`sel.on("dblclick.zoom", null)` の 1 行で d3 の拡大を切る。

- 利点: `onActivate` の契約（「double-click / "open" intent on a node」）が実際の挙動と一致する。拡大はホイールとビューリセットで足りる
- 欠点: ダブルクリック拡大に慣れていると、拡大手段が 1 つ減ったように感じる

**B: 現状維持（拡大のまま）**。`onActivate` の口をダブルクリックからは外し、コメントとドキュメントを実態に合わせる。

- 利点: 触らない。d3 既定の操作感を保つ
- 欠点: 「効かないショートカット」が残る（押しても開かない = #434 S-1 と同じ壊れ方）

**放置時**: 何もしない（B 相当・現状維持）。実装は Issue 化してから着手する。

## D-20260802-sched-1: outbox エントリを実装 PR に同梱するか、tracker と同様に merge 後へ回すか

**背景**: D-20260801-main-1 は tracker（memory/history）を実装ブランチに載せないとだけ規定していて、`.claude/comm/outbox/` の扱いは未規定。outbox も「同じファイルの先頭への追記」なので、複数ブランチが並行すると tracker と同じ衝突パターンになる。今セッションは #555 / #551 / #553 の 3 本を同一 worktree から連続して出すため、各 PR に outbox エントリを載せると 2 本目以降が必ず衝突する。

**A: 実装 PR に同梱する（従来型）**。エントリがその PR と一緒に main へ届く。

- 利点: chat-main が merge 時点で outbox の起票依頼まで読める
- 欠点: 並行 PR で outbox が衝突する（tracker で実証済みのパターン）

**B（既定・今セッションはこれで進行）: tracker と同じく実装 PR では触らず、merge 後にまとめて 1 commit**。それまで worktree の作業ツリーに未コミットで保持する。

- 利点: 衝突ゼロ。D-20260801-main-1 と一貫
- 欠点: chat-main への伝達が merge 後まで遅れる（緊急の連絡は PR 本文 / PR コメントに併記して補う）

**放置時**: B（安全側）。今セッションの outbox エントリは未コミットのまま保持し、要点は PR 側に併記する。
