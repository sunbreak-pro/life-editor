## D-20260811-main-1: Epic #627（保存ボタン統一）の対象範囲をどこで切るか

- 背景: 起票時の下書き 5 行に対し、2026-08-11 の grep 実測で編集面は **19 行**（Note の対象外行を含む）になった。差が 2 行を大きく超えたため、子 Issue の一斉起票を止めてここへ積んだ（実測表は Issue #627 本文が正）。判断が要るのは 3 点 — (1) **Settings 4 パネル**は書き込み先が localStorage で DataService を経由しない（`ThemeContext.tsx:176` / `useDayStartHour.ts:25`）。保存ボタン統一の対象に含めるか (2) **Briefing 2 面**（今日の宣言 / 夜の振り返り本文）は Note・Daily と同じ自動保存系。対象外へ寄せるか (3) **作成専用フォーム**（`ItemCreatePanel` / `TaskAddDialog` / `QuickAddSheet` / `QuickCaptureSheet`）は「既存要素の編集」ではないと判断して表から外したが、含めるか
- A: **DataService に書く「既存要素の編集」だけを対象にする**（推奨 — Settings は localStorage で即時反映が期待される種類の設定、Briefing は Note / Daily と同じ長文自動保存系、作成フォームはもともと「作成」ボタンで確定している。この線なら子 Issue は Schedule 繰り返し / Tasks の TaskDetailPanel + 本文 / Work の Pomodoro 数値 + AudioMixer / Tags の改名 に絞られる）
- B: 画面に出る編集はすべて対象にする（Settings と Briefing も保存ボタンにする。一貫性は最大になるが、Settings のテーマ切替や文字サイズは「押すまで反映されない」体験になり、Briefing は Note / Daily を対象外にした理由と矛盾する）
- C: 段階を分ける（まず A の範囲で子 Issue を配り、Settings / Briefing は 1 本の別 Epic に切って後日判断する）
- 放置時: 子 Issue を起票しない（Epic #627 は棚卸し済み・fan-out 保留のまま）。段階 1（Schedule の保存ボタン = PR #681）は着地済みなので実害は「横展開が進まない」だけ
- 期限感: 急がない。ただし各レーンが個別に保存ボタンを足し始める前に決めたい（バラバラの流儀が再生産される）
