### D-20261007-main-1: 外側に作る拡張アプリを NG-3 の例外として認め、V3 の「家計簿は汎用 Database で表す」を拡張アプリに置き換えるか

- B: NG-3 は文面のまま残し、拡張アプリは例外として 1 件ずつこうだいさんが承認する。V3 は変えない
- 放置時: 計画書は Draft のまま、窓口の実装に着手しない（Step 1 で止まる）
- 期限感: 窓口の着手前まで

### D-20261007-main-3: 窓口をどこに置くか（A 今の Remote MCP を広げる / B 専用の Worker を別に立てる / C Edge Function の HTTP API / D 拡張アプリ側に中継）。MCP の形で出すか、普通の HTTP API で出すか

- 背景: 計画書の「検討した代替案」の表。公開して使うので、どの案でも鍵をブラウザに置かない道（R4）と、確認専用アカウントに向ける道（R8）が要る。
- A: B 専用の Worker を別に立て、MCP（JSON-RPC）の形のままハンドラと検査を共有する（推奨 — スマホのコネクタ用の入口と分けるので、拡張アプリ用の鍵・CORS の変更がスマホ側を壊さない。ハンドラが 1 本のまま偽物との一致も取れる。改める決まり = `.claude/CLAUDE.md` §5「入口は 2 本」が 3 本になる）
- B: 今の Remote MCP を広げる（配布・シークレットが 1 つで済む。代わりに公開面が広がり、スマホのコネクタと同じ Worker に CORS と鍵の仕組みが入る）
- C: Supabase Edge Function の HTTP API（RLS がそのまま効く。代わりに MCP のハンドラと検査を共有しにくく、仕様が 2 つに割れる）
- D: 拡張アプリ側に中継を置く（life-editor 側の変更が小さい。代わりにサーバーを持たない SubscRecorder の形と合わない）
- 放置時: 置き場が決まるまで Scope を確定せず、Step 2 以降に着手しない
- 期限感: D-20261007-main-1・2 と同時
