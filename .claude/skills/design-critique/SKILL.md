# design-critique — 見た目を測って採点する

料理でいうと、計量カップ（計測）と味見の基準（採点表）の役目です。新しい献立（デザイン案）は Claude Design に考えてもらい、このスキルは「前より良くなったか」を同じ物差しで確かめるために使います。

- **道具の選び方の根拠**: `docs/reports/2026-09-28-design-tooling.html`（2026-09-28 ユーザー確定）。
- **UI を作るときの規約**（トークン・4 状態・アクセシビリティ・motion の 3 帯）は `frontend-react-designer` が正本です。このスキルは規約を満たした上での「見た目の良し悪し」を扱います。
- **崩れ・はみ出し・タップ寸法の機能的な確認**は `playwright-verify` の担当です。

## 誰が何をするか

| 役割       | 担当                                        | 理由                                                                    |
| ---------- | ------------------------------------------- | ----------------------------------------------------------------------- |
| 撮影と計測 | chat-main（Playwright MCP）                 | 実ブラウザと dev server は chat-main だけで起動する（CLAUDE.md §7.4）。 |
| 採点       | 新しく起動した general-purpose エージェント | 案を作った人・実装した人が採点すると甘くなるため。                      |
| 案出し     | Claude Design（こうだいさんの操作）         | 案を広く出すのが得意で、良し悪しの判断は苦手なため。                    |
| 選択       | こうだいさん                                | 見た目の好みは人の判断。                                                |

## 手順

### 1. 条件を揃えて撮影する

1 画面につき次の 4 通りを撮影し、scratchpad に保存します。直す前と後で、同じデータ・同じ条件で撮ります。

| 幅               | テーマ          |
| ---------------- | --------------- |
| Desktop 1280×800 | ライト / ダーク |
| Mobile 390×844   | ライト / ダーク |

- 空の状態・ローディング・エラーが別の見た目になる画面は、その状態も撮ります。
- スクリーンショットの保存先の罠はメモリ「Verification command pitfalls」を参照します。

### 2. 数値を集める

同じ 4 通りそれぞれで `scripts/measure.js` を実行します。

- `browser_run_code_unsafe` に `filename: ".claude/skills/design-critique/scripts/measure.js"` を渡します。中身を `code` に貼り付けないでください。整形で末尾に `;` が付いた状態だと SyntaxError になります。
- 読み込めるのはメインのリポジトリ配下のファイルだけです（Playwright MCP の許可範囲）。worktree の中のファイルは読めません。
- 画面の一部だけを測るときは、先に `browser_evaluate` で `() => { window.__designCritiqueRoot = "main"; }` のようにセレクタを置きます。
- 返り値の JSON を `<画面>-<幅>-<テーマ>-<before|after>.json` の名前で scratchpad に保存します。

### 3. 採点する

general-purpose エージェントを新しく起動し、次の 3 つを渡して `references/rubric.md` で採点させます。

- 手順 1 のスクリーンショットのパス
- 手順 2 の JSON のパス
- 比較の相手にする画面（Schedule と Materials）の同じ条件のスクリーンショット

エージェントには「ファイルを変更しない」「`visual-inspect` スキルで切り抜いて拡大して見る」「点には数値とどこを見たかの根拠を付ける」を必ず指示します。返ってきた所見は、メインが 1 件ずつスクリーンショットで確かめてから採用します（9 月の画面点検では、エージェントの所見の一部が実測で覆りました）。

### 4. 案を出して選ぶ（見直しのときだけ）

- 手順 3 の「直す候補」を、Claude Design に渡す指示書（`.claude/docs/design/briefs/`）の「今の UI の課題」に入れます。
- Claude Design の案は、手順 1〜3 と同じ物差しでは測れません（実ブラウザの画面ではないため）。案の段階では採点表の目視の項目だけで比べ、こうだいさんが 1 つ選びます。
- Claude Design の生成物と規約が食い違ったときは規約を優先し、食い違いを表にして報告に入れます（7 月の実装で決めたルール）。

### 5. 実装後に測り直す

実装が merge されたら、手順 1〜3 をもう一度かけます。PR か Issue に、直す前と後の点と数値の差を表で残します。

## 注意

- 余白の段階（`measure.js` の `SPACING_STEP_PX`）とアニメーションの帯（`MOTION_BANDS`）は仮の値です。`shared/src/styles/tokens.css` に段階が入ったら、その値に合わせてスクリプトを直します。
- `browser_run_code_unsafe` は実行したコードを結果に全文表示します。1 回あたり数千トークンを使うので、条件を 4 通りに絞って回します。
- jsdom には座標が無いため、このスクリプトは vitest では使えません。
