# D-20260811-refactor-2: `window.confirm` を自前ダイアログに置き換えるか（計画書 §C3 PR 4 の 1 項目）

## 背景

（キュー原文 = `comm/decisions/chat-refactor-core.md`。昇格とキューからの除去は chat-main が代行した）

#670 C3 PR 4 で着手しようとして、**計画書とコード内の記録が食い違っている**のを見つけた。計画書は「`window.confirm` を既存 `RepeatScopeDialog` の形へ（規約ドリフト是正）」としているが、コード側は 3 箇所で「意図してそう選んだ」と明記していた:

- `web/src/schedule/CalendarTab.tsx:1492`（#628）— 「a browser confirm is the one dialog that cannot be missed on either platform」
- `web/src/settings/SettingsScreen.tsx:124`（#216）— 「window.confirm is the app's existing lightweight confirm affordance for a one-shot destructive action」
- `web/src/tasks/KanbanView.tsx` / `CalendarTab.tsx:1765`（#573）— 上の 2 つが参照している元パターン

つまり調査時は「ドリフト（統一漏れ）」に見えたが、実際は**過去に下した判断**。ドリフト是正として黙って剥がすと、その判断を無言で覆すことになるので P-008 に従い実装せずキューへ積んだ。

キュー起票時の影響範囲は 6 箇所（CalendarTab 4 / SettingsScreen 1 / KanbanView 1）+ 共有 `ConfirmDialog` 新設 + en/ja 文言、という見積もりだった。

## 選択肢と裁定

- A: 現状維持（却下 — キュー時点の推奨だったが、ユーザー回答 2026-08-12「自前ダイアログを実装」で落選）
- B: **全箇所を共有 `ConfirmDialog` に置き換える**（**採用** — ユーザー回答 2026-08-12）
- C: `askDiscard` 以外だけ置き換える（却下 — B が選ばれたため。同期契約の扱いは実装側の注意点として残る）

## 前提が変わった点（昇格時の実測 = main `bdbf1da1`）

キュー起票（2026-08-11）から回答（2026-08-12）までの間に **#707 / #736 / #628 が着地し、見積もりの前提が変わっている**:

- 共有 `ConfirmDialog` は**新設ではなく既に存在する**（`shared/src/components/ConfirmDialog.tsx`・#707）。`CalendarTab` / `KanbanView` / `TagEditModal` / `UnsavedGuardContext` が既に使っている
- 残る素の呼び出しは **6 箇所ではなく 3 箇所**（`SettingsScreen.tsx:131` の confirm / `KanbanView.tsx:329` の confirm / `KanbanView.tsx:320` の alert）
- したがって B の実体は「全面置換」ではなく「取り残された 3 箇所の回収」になる

- 実装 Issue = **#781**（`[shared-fix]`）
