# D-20260830-main-2: #1135 方向 (b)（regen 時に gh で PR 実状態を引く）は実装するか

## 背景

（事後記録 = chat-main 自裁。UX 分岐ではなく tooling の技術判断のため recorded で直接起票）

#1135（memory/ の「進行中」が実態と乖離）には 2 方向があった。(a) = 書き手のいないレーンを RETIRED マーカーで集計から外す（PR #1295 で機構 + 21 レーンへの付与が着地済み・regen-index のスキップ分岐は vendor 版 + この Windows 機の hooks-lib 版へ移植済み）。(b) = regen-index 実行時に `gh` で PR の実状態を引き、「進行中」の記述と突き合わせて stale を検出する案。r4 の chat-main 手番の残りとして「(b) を別 Issue に切るか、見送って #1135 を (a) 完了とするか」の扱い決めが巡回ループに残っていた。

## 選択肢と裁定

- A: (b) を実装する別 Issue に切る（却下）
- B: (b) は見送り、#1135 は (a) で完了扱いとして close 判定をユーザーへ提示する（**採用** — 2026-08-30 chat-main 記録）

## 理由

1. regen-index は SessionStart hook で**全セッション・全 worktree が毎回実行する経路**で、外部版スクリプトの設計前提は「idempotent, no network」。`gh` 呼び出しを入れるとオフライン / headless（夜間の `claude -p` レーン含む）に常設の失敗経路が増える
2. INDEX の実消費者（issue-prompter の収集手順 / chat-main の巡回ループ）は**既に gh を直接叩いて実状態で判定している**。派生ビューへ live データを混ぜても判定の正は変わらず、鮮度検査が二重になるだけ
3. stale の主因だった「書き手のいない 21 レーン」は (a) の RETIRED 機構で構造的に消えた。実測 = INDEX「進行中」29 行 → 7 行（2026-08-30・この Windows 機）

## 却下案が復活する条件

アクティブレーンの「進行中」の stale が再び判定事故（手番の誤配布・二重着手）を起こしたら、**hook ではなく issue-prompter / dev-digest 側のオンデマンド照合**として実装する。毎セッション実行の hook に network を入れない前提は維持する。
