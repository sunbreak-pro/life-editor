# D-20261021-main-1: 取ったデータを端末に保存し、一部をオフラインでも使えるようにするか

## 背景

（キューを経ず、chat-main の会話で直接聞いて回答を得た。問いと回答は会話から再構成した）

- #2290 で通信量を測った結果、1 日の見積りは環境音ありで約 11MB、なしで約 6MB だった。こうだいさんから「通信量とロード時間を減らすために、端末に一時的に保存できないか」「一部であればオフラインでも使えないか」と問いがあった。
- これまでの方針は次の 2 つだった。
  - D-20260818-refactor-1 で、取ったデータはメモリにだけ置き（A-1）、localStorage にも置く案（A-2）は却下した。古い形のデータが端末に残り続ける危険があるため。
  - 移行の計画書で「常時オンライン前提」「オフライン編集はやらない」「Service Worker は採用しない」と決め、要件として「オフライン不要」と記録していた。
- chat-main が出した段階は次のとおり。
  - 段階 0: 回線が戻ったら、切れていたあいだの変更を取り直す。
  - 段階 1: 取ったデータを IndexedDB に保存し、前回から変わった分だけを取る。アプリ本体を Service Worker で端末に置き、オフラインでも前回までのデータを見られるようにする。
  - 段階 2: Daily への書き込みと Todo の追加を、圏外でも受け付けて回線が戻ったら送る。
  - 段階 3: すべての画面でオフライン編集する。

## 選択肢と裁定

- 段階 0・1・2 を進める（**採用** — こうだいさん回答 2026-10-21）。段階 2 は Note まで広げる。ただし、オフラインのあいだに表示するノートは、オフラインで新しく作ったものとピン留めしたものだけにする。端末に置く量を抑えるため。
- 書き込みがぶつかったときの扱い（**採用** — こうだいさん回答 2026-10-21。計画書の「競合ルール」）。送る前に元の版を比べ、ずれていたら 3-way merge で合わせる。同じ段落を両方で直していたら、ノートはサーバーの版を残し、圏外で書いた版を別のノートとして残す。Daily は両方を本文に並べる。
- 「新規作成とピン留めだけ表示」の読み方（**採用** — 同日、chat-main の仮定をこうだいさんが承認）。圏外で表示・編集できるのは、ピン留めしたノートと圏外で作ったノートだけ。ほかのノートは圏外のあいだ一覧に出さない。
- 段階 3: すべての画面でオフライン編集する（却下 — 書き込みがぶつかったときの決まりを全領域に作る必要があり、大きさに見合わない）。
- 段階 0 だけ進めて、端末への保存とオフラインはやらない（却下 — こうだいさんが表示の速さと通信量の両方を減らしたいと判断した）。

## 却下案が復活する条件

- 段階 2 を使ってみて、Daily・Todo・Note 以外の画面でもオフラインで書きたい場面が繰り返し出たとき、段階 3 を領域ごとに再検討する。

## 波及

- D-20260818-refactor-1 の A-2 の却下を置き換える。同じ決定の A-1（メモリのみの stale-while-revalidate）は、端末への保存の下で引き続き使うので有効のまま残す。このため、その決定全体を superseded にはしない。古い形のデータが残る危険には、保存するデータに版番号を付け、版が変わったら捨てて取り直すことで対処する。
- 移行の計画書の §3 表「オフライン」行と §9 Non-goals の 2 項目を書き換える。
- `docs/vision/core.md` の「オンライン前提」の注記を書き換える。
- 実装の段取りは計画書 `docs/vision/plans/2026-10-21-offline-cache.md` が正本。段階 0 は #2329。
