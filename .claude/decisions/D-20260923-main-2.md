# D-20260923-main-2: 配布前に埋める 4 点を Issue にして、どの順に着手するか

## 背景

（キューを経由せず、2026-09-23 の棚卸し報告書 `docs/reports/2026-09-23-product-audit.html` §3 の「配布ユーザーが最初に踏む順」からチャットで問い、回答「きめる」= Issue 化して順を決める、を得た。以下は報告書とチャットから再構成した）

- 製品基準の監査で、認証・RLS・法務文書・テストは水準に届いていた。欠けていたのは配布まわりの 4 点で、どれも $0 のまま埋められる:
  1. 確認メールの送信元が Supabase 内蔵 SMTP のまま（毎時数通の上限。数人同時に登録すると届かない）
  2. Desktop の Electron が 33 系で、約 17 か月セキュリティ更新を受けていない（現行 44 系・サポートは直近 3 メジャー）
  3. 自分のデータを持ち出す手段が無い（規約は「控えは利用者自身で」と求めている）
  4. アプリ内にヘルプ・問い合わせの導線が無い（唯一のリンクは規約文中の GitHub Issues）

## 選択肢と裁定

- A: 4 件を Issue #1986 / #1987 / #1988 / #1989 として起票し、着手順を **SMTP（こうだいさんの手番・並行）→ Electron 更新 → エクスポート → 問い合わせ導線** とする（**採用** — ユーザー回答 2026-09-23「きめる」。順序は chat-main の自裁: SMTP は外部サービス登録と DNS 反映に日数がかかるため最初に始めて並行させる。Electron はセキュリティで、Claude だけで進められる。エクスポートは規約との整合。問い合わせ導線は連絡先の決定がこうだいさんの手番なので最後）
- B: 利用者が最初に踏む順（SMTP → Electron → エクスポート → 導線）をそのまま直列にする（却下 — SMTP の待ち時間で他 3 件が止まる）
- C: 配布人数を絞って 4 件とも先送りする（却下 — サインアップ開放（D-20260829-main-1）と両立しない）
