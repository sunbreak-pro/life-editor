# D-20261010-mcp-tools-1: 拡張アプリは窓口を迂回しない。窓口が持つ 2 つの約束（`bumpMeta` と、payload 作成失敗時の meta 削除）

## 背景

拡張アプリ用の窓口の計画書（Step 9 / 要望 R9）が、この約束を決定記録に残すことを求めている。ユーザーに選択を求める分岐ではないため、計画書の Step 9 に沿った事後記録（`recorded`）として書く。

迂回の道は実際にある。Supabase の anon key は公開値で（`supabase/README.md:9-13`）、life-editor のログインを持つアプリは、窓口を通らずに PostgREST へ直接書ける。直接書くと、窓口のハンドラが共通の部品に任せている次の 2 つが働かない。

1. **`bumpMeta`**（`mcp-server/src/utils/items.ts`）。項目への書き込みのたびに `items_meta.updated_at` を進める。この列が Cloud Sync の LWW cursor で（CLAUDE.md §3.3）、`<role>_payload` は `updated_at` を持たない。payload だけを直接書き換えると cursor が動かず、ほかの端末は変更に気づかない。
2. **payload 作成失敗時の meta 削除**（同ファイルの `insertItem`）。項目の作成は「`items_meta` の INSERT → `<role>_payload` の INSERT」の 2 手で、2 手目が失敗したら 1 手目の meta 行を hard delete して、meta だけの孤児を残さない（db-conventions §10.5）。直接書く側がこの後始末を忘れると、payload を持たない `items_meta` の行が残る。

## 裁定

拡張アプリは life-editor のデータを、窓口（拡張アプリ用の専用 Worker。D-20261007-main-3 = A）を通してだけ読み書きする。Supabase の REST / Realtime / SDK を直接使って `items_meta` や `<role>_payload` に書かない。

窓口の側が約束するのは次の 2 つで、どちらも既存の共通部品に任せる。窓口のハンドラは、この 2 つを通らない書き込み経路を持たない。

- **`bumpMeta`**: 窓口の書き込みはすべて、項目の `items_meta.updated_at` を進める。
- **後始末**: 作成の途中で失敗したら、作りかけの meta 行を消す。

守らせる場所は life-editor の外にある。pdca-harness の契約（拡張アプリは Supabase に直接つながない）と、その検証役が見る。life-editor の側では、この記録と窓口の仕様ファイル（#2144）が根拠になる。DB の側で直接書き込みを止める仕組み（トリガーや権限の絞り込み）は、この記録では作らない。

もう一つ、窓口が付ける作成元の列（`items_meta.origin_app` / `origin_key` / `origin_request_hash`、#2147）は、作成時に 1 度だけ書く列として扱う。持ち主の JWT なら DB は UPDATE を通すので、DB は守らない。拡張アプリも窓口も、作成のあとにこれらの列を更新しない。

## 却下案が復活する条件

迂回した書き込みが実際に見つかったとき、DB の側で止める案（`updated_at` を DB 側で必ず進めるトリガーや、拡張アプリのログインに書き込み権限を与えない構成）を、新しい決定として検討する。今は、窓口の作り込みを DB 側の強制より先に置く。
