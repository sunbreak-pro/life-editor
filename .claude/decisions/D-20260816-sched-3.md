# D-20260816-sched-3: バルク生成が 1 件の衝突で全滅するのを、衝突分を外した撃ち直しに変えるか

## 背景

（キュー原文 = `comm/decisions/chat-schedule-refine.md`）

- 背景: Issue #933 / PR #966 / `shared/src/services/SupabaseScheduleItemsService.ts`。#933 の指示どおり、バッチ内重複の dedupe（本題）は実装済みだが、Issue が「この Issue の中で判断してよい（挙動が変わるならキューへ）」と書いた**R2 cleanup の全滅**は挙動変更なので分離した。`events_payload` への INSERT は 1 文なので 23505 が出ると全行が巻き戻り、cleanup が直前の `items_meta` を全件消す = 30 日分の月埋めが 0 件になる。**なお cleanup 自体は正しい**（payload が 1 行も入っていない以上、meta は全部が孤児）。問われているのは「その後どうするか」
- A: **現状維持（推奨 — 事前チェックが 2 系統（DB の live 行 + バッチ内）そろった今、23505 に到達するのは生成器との競合だけで、次の effect 発火で自然に埋まる）**。リトライを足すと「衝突しやすい状況で余計に書きに行く」経路が 1 本増える
- B: 23505 を掴んだら衝突しているペアを DB から引き直して除外し、**残りで 1 回だけ撃ち直す**（#932 で restore に入れた「チャンクを id 単位で撃ち直す」と同じ発想の生成版）。競合しても当日分が埋まる代わりに、失敗時の往復が最大 2 倍になる
- 放置時: A のまま（#933 / PR #966 は現状で完結している）。B を採るなら別 Issue を起票して独立 PR で行う
- 期限感: いつでも（#966 の merge をブロックしない）

## 選択肢と裁定

- A: **現状維持**（**採用** — ユーザー回答 2026-08-16）。理由: #933（PR #966）で事前チェックが 2 系統（DB の live 行 + バッチ内の自己衝突）そろったので、23505 に到達する経路は**別プロセスの生成器と同時に走った瞬間だけ**に絞られた。その状況は次の描画で effect が再発火すれば自然に埋まるため、失われるのは「一瞬 0 件に見える」ことだけ。対して撃ち直しは、**最も衝突しやすい瞬間に余計な往復を 1 本増やす**経路を常設することになる
- B: 衝突分を外して 1 回だけ撃ち直す（却下 — 得られるのは競合時に当日分が 1 描画ぶん早く埋まることだけで、常設の複雑さと失敗時 2 倍の往復に見合わない）

## 却下案が復活する条件

- 実運用で「月が 0 件のまま埋まらない」が観測されたとき（= 次の effect 発火による自然回復が効いていない証拠）。そのときは B を独立 Issue として起票し、撃ち直しを入れる
- 生成器が複数プロセスから常時走る構成に変わったとき（現在は単一クライアント前提）

## 波及

- `bulkCreateScheduleItems` の R2 cleanup は現状（全滅 → 次の発火で回復）のまま。#933 / PR #966 で完結扱い
- **#932 の restore 側（`bulkRestoreScheduleItems`）とは方針が異なる**点に注意 — あちらは「ユーザーが今押した復元」なので拒否された分を返す価値があるが、こちらは自動生成なので黙って次の発火に任せてよい。同じ 23505 でも扱いが違うのは、**ユーザー操作の結果かどうか**で分かれている
