# D-20260812-sched-1: モバイルの Todo 一覧行にも削除の導線を足すか

## 背景

（キュー原文 = `comm/decisions/chat-schedule-refine.md`）

- 背景: #775 / PR #784。詳細シート（`shared/src/components/TaskDetailPanel.tsx`）には削除を足したが、日リストの行そのものには足していない。行は `shared/src/components/schedule/AgendaList.tsx` で Desktop サイドバーと共用で、Desktop 側の Todo トレイ（`TodayTodoTray.tsx:138`）には既に行内ゴミ箱がある
- A: 現状維持（推奨 — 行内ゴミ箱は完了チェックボックスの親指 1 本分となりに破壊的操作を置くことになる。#761 で行タップが詳細シートを開くようになったので、削除は 1 タップ先の「確認を出せる面」にある）
- B: 行を左スワイプで削除を出す（iOS の標準作法。ただしこのアプリにスワイプ操作の前例が無く、`AgendaList` の DnD / 横スクロールとの当たり判定を新規に設計することになる）
- C: 行内に小さなゴミ箱を出す（Desktop トレイと同じ形。実装は最小だが誤爆が一番しやすい）
- 放置時: A のまま（PR #784 は A で出している）。この判断のために #775 を止めない
- 期限感: いつでも（#775 の merge を待たない）

## 選択肢と裁定

- A: **現状維持 = 一覧行に削除の導線を足さない**（**採用** — ユーザー回答 2026-08-12）。理由: 行をタップして詳細を開き、そこから削除する。この形なら**削除は必ず「確認を出せる面」にある**ことになり、完了チェックボックスの隣に破壊的操作が並ばない。#761 で行タップが詳細シートを開くようになったので、A のままでも削除は 1 タップ先に届く
- B: 左スワイプで削除を出す（却下 — iOS の標準作法ではあるが、アプリ内にスワイプ操作の前例が無く、`AgendaList` の DnD / 横スクロールとの当たり判定を新規設計することになる。得られるのは 1 タップの短縮だけで、確認面を経由しない削除が増える）
- C: 行内に小さなゴミ箱を出す（却下 — 実装は最小だが、完了チェックボックスの真横に取り消しの効かない操作が並ぶ。指 1 本ぶんの距離で「完了」と「削除」を取り違える誤爆が一番起きやすい形になる）

## 却下案が復活する条件

- 詳細シート経由の削除が「回数が多くて面倒」と実測で判明した場合（例: 1 日に何件も削除する使い方が定着した場合）。その場合も C（行内ゴミ箱）ではなく B（スワイプ + 確認）を先に検討する — 誤爆耐性が違うため
- アプリ全体でスワイプ操作の前例ができ、`AgendaList` の DnD と共存する当たり判定の設計コストが下がった場合

## 波及

- **削除は確認を出せる面に集約する** — これが本裁定の一般則。Todo の削除導線を新設するときは「一覧行に直接置く」ではなく「詳細（シート / パネル）から出す」を既定とする
- [#786](https://github.com/sunbreak-pro/life-editor/issues/786)（Kanban のカードから Todo を削除できない）の設計前提。カードに直接ゴミ箱を生やすのではなく、カードから開く詳細（`TaskDetailPanel`）側に削除を置く方向で設計する
- Desktop の Todo トレイ（`TodayTodoTray.tsx:138`）にある行内ゴミ箱は既存のまま据え置く（マウス操作は誤爆の距離感が違うため、本裁定はモバイルの一覧行を対象とする）
- コード変更は無し。PR #784 が A の形で既に着地している
