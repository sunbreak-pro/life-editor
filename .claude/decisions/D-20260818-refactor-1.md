# D-20260818-refactor-1: セクション切替の体感ロード、どの案から着手し、キャッシュはどこに置くか

## 背景

（キュー原文 = `comm/decisions/chat-refactor-core.md`）

- #1038 の実測（`docs/reports/2026-08-18-section-switch-load.md`）。体感の主因は本数ではなく、**切替のたびに前回値を捨てて取り直しが返るまで骨組みを見せる**こと（materials 復帰 = 5 本を全件再取得・キャッシュ利用 0 本）。副次的に、その画面が表示に使わない読みが schedule で 3 本 / connect で 2 本、Materials のタブ切替で 3 本ある
- A: 案 A（stale-while-revalidate）から（推奨）／ A-1 = メモリのみ ／ A-2 = localStorage にも置く
- B: 案 B（無駄取りの削減）から
- C: 両方やる（A → B の順で別 Issue 2 本）
- 放置時: #1038 は調査完了として保留・実装 Issue は起票しない

## 選択肢と裁定

- A-1: **stale-while-revalidate をメモリのみで入れる**（**採用** — ユーザー回答 2026-08-19）。理由: 「空の時間」を消せるのはこの案だけで、`useDomainLoad` + 小さな store 1 本に収まる（前例 = `useLazyStalePool`）。永続化しないのでスキーマ変更時の残骸を抱えない
- A-2: localStorage にも置く（却下 — リロード直後の初回表示にも効く代わりに、古いスキーマの残骸というリスクを常設する）
- B / C: 無駄取りの削減（今回は不採用 — 体感の主因ではない。必要になったら別 Issue を起票する）

## 却下案が復活する条件

- A-1 を入れても初回ロード（リロード直後）の体感が問題として残ったとき → A-2 を再検討
- 実ブラウザ計測（#994）で「表示に使わない読み」がネットワーク待ちの主因だと出たとき → B を起票

## 波及

- 実装 Issue **#1101** を起票。#1038 は調査 Issue として close 済み
