# D-20260812-sched-2: 繰り返しの削除を Undo したとき、どこまで元に戻すか

## 背景

（キュー原文 = `comm/decisions/chat-schedule-refine.md`）

- 背景: #708。繰り返しを消して Undo すると、ルーチンの行だけが戻り、一緒に消えたオカレンスと「種になっていた手動作成イベント」は消えたまま。代わりにジェネレータが当日分を**新しい id で作り直す**ため、見た目は戻ったようで中身が入れ替わっている（2026-08-11 chat-main の実測 = `si-1fe619b3` / `si-25634b94` が復活せず、`schedule-b7d3c2d2` も削除済みのまま、新 `si-9d18df3c` が生成）
- A: ルーチン + オカレンス + 種イベントを**すべて元の id で復元**する（推奨 — 「Undo = 直前の状態に戻る」に忠実。ソフトデリートの復元なので技術的に可能。とくに種イベントはこうだいさんが手で作った予定なので、消えたままなのは驚きが大きい）
- B: **種イベントだけ復元**し、オカレンスは再生成に任せる（オカレンスは派生物という整理。id は変わる）
- C: 現状のまま許容し、**削除確認の文言で予告**する（「取り消しても元の予定は戻りません」）
- 放置時: #708 は保留のまま。他の Issue（#789 / #774 / #790）を先に進める
- 期限感: いつでも（他 3 件の PR とは独立）

## 選択肢と裁定

- A: **ルーチン + オカレンス + 種イベントをすべて元の id で復元する**（**採用** — ユーザー回答 2026-08-13）。理由: Undo は「直前の状態に戻る」であって「似た状態を作り直す」ではない。とくに種イベントはユーザーが手で作った予定で、繰り返しを消して取り消したのに元の予定が消えたままなのは驚きが大きい。`softDeleteRoutine` が消した id の一覧を既に戻り値で返しており（`deletedScheduleItemIds` = オカレンス + 種イベント）、ソフトデリートの復元なので技術的にも素直に実装できる
- B: 種イベントだけ復元（却下 — 「オカレンスは派生物」という整理自体は筋が通るが、復元後の id が変わる点は A と同じ問題を残す。手で動かした・完了にしたオカレンスも作り直しになるため、実測で観測された「中身が入れ替わる」現象がオカレンス分だけそのまま残る）
- C: 現状維持 + 文言で予告（却下 — 実装は最小だが、直せるバグを仕様として固定することになる。ソフトデリートの復元で戻せると分かっている以上、「戻りません」と予告するのは説明としても弱い）

## 却下案が復活する条件

- カスケードが極端に大きいルーチン（数年分のオカレンス）で Undo の待ち時間が体感に響くと実測された場合。その場合も C ではなく、復元を可視範囲優先にする等の段階化を先に検討する

## 波及

- **順序が本体**: オカレンスを戻してから、ルーチンをライブ一覧へ戻す。ジェネレータはライブ一覧の変化で起動し、その読み取りは `is_deleted` を除外するため、後から戻したオカレンスはジェネレータから見えず同じ日に新しい id を作ってしまう（これが #708 の実測そのもの）
- `DataService` に `bulkRestoreScheduleItems(ids)` を追加（`bulkSoftDeleteScheduleItems` の逆。1 件ずつ復元するとオカレンス数だけ往復が増えるため chunk 単位）
- `deleteRoutine(id, opts)` に `onCascadeChanged` を追加。ルーチン一覧は shared 側が持つが、戻ってくる行はホストの可視範囲ストアにあるため、ホストが再読込する合図が要る
- Trash からの `restoreRoutine` は対象外（本裁定は Undo の話に限る）。Trash 復元でオカレンスも戻すかは別途
