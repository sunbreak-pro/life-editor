# D-20260830-main-3: Intel Mac 向け x64 `.dmg` を配るか

> **ID について**: キューでは `D-20260830-main-1` の ID で起票されていたが、同じ ID が同日の「退役レーンの memory を chat-main が畳んでよいか」（[D-20260830-main-1](./D-20260830-main-1.md)）に先に使われ、`-2` も採番済みだったため、昇格時に `-3` へ振り直した。キュー原文・計画書 §R3・`release-desktop.yml` / `desktop/README.md` のコメントが指していた「x64 dmg の判断」はすべて本ファイルを指す。

## 背景

（キュー原文 — 回答に伴い本 PR でキューから削除。起票 = chat-main 2026-08-30）

- 背景: #1301 / 計画書 `docs/vision/plans/2026-08-30-desktop-app-packaging.md` §R3。`macos-latest` は arm64 ランナーなので x64 dmg はクロスビルドになり、**CI では一度も起動できないまま配ることになる**。現行 `desktop/electron-builder.yml` は arm64 + x64 の両方を宣言している
- A: arm64 のみ配る（推奨 — 「検証できないものは配らない」で揃う。Intel Mac の要望が出てから足せばよい）
- B: 両アーキ配る（Intel Mac ユーザーが居るなら初手から届く。ただし壊れていても気付けない）
- 放置時: 現行宣言のまま両アーキをビルドするが、**受け入れ対象は arm64 のみ**。x64 は Release に載せず artifact に留める（安全側）
- 期限感: #1301 の Release 発行前まで

## 選択肢と裁定

- A: arm64 のみ配る（**採用** — ユーザー回答 2026-09-09「推奨のまま A で OK」。検証できない成果物を配らない原則で揃う。x64 のビルド時間も消える）
- B: 両アーキ配る（却下 — ランナで一度も起動できないバイナリを配ることになり、壊れていても気付く経路が無い）

## 却下案が復活する条件

Intel Mac のユーザーから要望が出たとき。`electron-builder.yml` の `mac.target[].arch` に `x64` を戻し、`release-desktop.yml` の release ジョブの検査（`*-arm64.dmg` を 1 件と数える）を両アーキ対応にすれば切り替わる。ただし配る前に Intel 実機での受け入れを 1 回挟む。

## 波及

- `desktop/electron-builder.yml`: `mac.target[].arch` から `x64` を削除
- `.github/workflows/release-desktop.yml`: macos 行の `extra_glob` と「upload unverified extras」ステップを削除（x64 をビルドしなくなるので `unverified-*` artifact も消える）
- `desktop/README.md` §macOS build: 「両方宣言しているが arm64 だけ受け入れ」の段落を「arm64 のみ」に書き換え
- 計画書 §R3 / 実測ログに回答を追記
- 初回 Release `desktop-v0.1.0`（2026-09-09 tag）は回答前の run なので x64 の artifact を持つが、Release 本体には arm64 だけが載っている（「放置時」の安全側どおり）
