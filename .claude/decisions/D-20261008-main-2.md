# D-20261008-main-2: 拡張アプリは別リポジトリに作るか、life-editor と同じリポジトリの新しいパッケージにするか

## 背景

キュー原文なし。2026-10-08 のチャットから再構成した。

Claude は 2026-10-08 のチャットで「同じリポジトリの新しいパッケージ（`web/` の隣）を勧める。`shared/` のデザイントークン・i18n・認証・DataService を使い回せるため」と意見を出した。こうだいさんは「repository は難しいが、別々にしたほうが後々管理が楽だと考える。もし手順がかなり増えるのならば統合する方針に切り替える」と答えた。

2026-10-06 に「拡張アプリは別のリポジトリに作り、窓口を通してつなぐ」と決まっている（`2026-10-07-extension-app-gateway.md` §Context・D-20261007-main-3 = A）。窓口を通す前提では、拡張アプリは life-editor のコードを import せず、窓口の仕様ファイルと偽物（#2144 / #2145 / #2150）だけを契約にする。

計画書 §リポジトリの分け方 で手順を数えた結果: 別リポジトリで増えるのは「窓口の仕様ファイルと偽物を取り込む」1 手順だけで、これは pdca-harness が無人で合否を判定するためにどのみち要る。

## 選択肢と裁定

- A: 別リポジトリ（**採用** — ユーザー回答 2026-10-08。手順は「かなり増え」ないので統合に切り替えない。2026-10-06 の決定を維持する）。**切替条件**: 次のどちらかに当たったら判断キューへ積む。(a) 拡張アプリが life-editor の `shared/`（`lumen-*` トークン・DataService・i18n）を import したくなったとき。別リポジトリでは npm に公開しないと参照できず、公開は $0 と相性が悪い。(b) 窓口の版上げ（#2144 の semver）が月に 1 回を超え、両リポジトリを同時に変える作業が常態化したとき
- B: 同じリポジトリの新しいパッケージ（却下 — こうだいさんは管理を分けたい。CI の `verify` ジョブにパッケージが 1 つ増える恒久コストもある）

## 却下案が復活する条件

上の切替条件 (a) か (b)。

## 波及

- 計画書 `.claude/docs/vision/plans/2026-10-08-extension-app-records-and-apps-section.md` §リポジトリの分け方（手順の表と切替条件）
- 最初の拡張アプリ（家計簿）の計画は、別リポジトリ側に書く（life-editor の `plans/` には置かない）
