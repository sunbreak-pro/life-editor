# D-20260812-materials-2: #674 の残り（PostgREST エラー判定の共通化）でエラー文字列の書式を統一するか

## 背景

（キュー原文 = `comm/decisions/chat-materials-refine.md`）

#674 の DoD のうち 2 つ（meta+payload ジョイン 8 箇所・ロック 6 メソッド）は PR #747 で畳んだ。残るのは「single / maybeSingle 系のエラー判定 126 箇所・二重キャスト 45 箇所」。ここを 1 本のヘルパに畳もうとすると、**エラー文字列の書式が 3 種類に割れている**のが壁になる。

| 書式                     | 例                                             | 使っている場所                   |
| ------------------------ | ---------------------------------------------- | -------------------------------- |
| `<method> <table>`       | `fetchTaskTree items_meta`                     | Tasks / Routines / ScheduleItems |
| `<method> <step> failed` | `listNotesUnified meta failed`                 | Notes / Dailies                  |
| `<method> <step>: <msg>` | `updateFutureScheduleItemsByRoutine titles: …` | ScheduleItems の一部             |

1 つの書式に畳むと**既存テストが assert している文字列が変わる**。#674 の共通ゲートは「挙動変更ゼロが原則」なので、勝手には倒せない。

**（キュー原文の）A: 書式を 1 つに統一する**（例: `<method> <step> failed: <msg>` に寄せる）。ヘルパが文字列を組み立て、呼び出し側は method と step だけ渡す。

- 利点: 126 箇所が本当に 1 箇所に畳まれる。今後どの層のエラーも同じ形で出るのでログが読みやすい
- 欠点: 「挙動変更ゼロ」を破る。文字列を assert しているテストの書き換えが要る（ざっと 20 箇所以上）。ユーザーに見えるエラー表示の文言も変わりうる

**（キュー原文の）B: 書式は各呼び出し側のまま、ラベルを引数で渡す**（PR #747 でジョインとロックに採ったのと同じやり方）。

- 利点: 挙動変更ゼロを保てる。テストは 1 行も変わらない
- 欠点: 「二重キャストと `if (error) throw` の定型」は消えるが、**ラベル文字列の重複は残る**。畳み込みの効果が半分になる

**放置時**: **#674 の残りに着手しない**（PR #747 で止める）。B なら判断なしで進められるが、A/B で成果物の形が変わるので、指示が無いうちは着手しないほうが安全。

**期限感**: いつでも（#674 は PR #747 で 4 分の 3 が着地する見込み）。

## 選択肢と裁定

> ⚠️ **ラベルではなく中身で読むこと**: 採択されたのは**「書式を揃えない」**で、ここに曖昧さはない。曖昧なのはラベルだけ — ユーザーに提示した AskUserQuestion では **A =「揃えない」/ B =「統一する」**の順に並べており、上のキュー原文（A = 統一 / B = 据え置き）とは A/B が逆だった。この注記はその経緯の記録であって、裁定に揺れがあるという意味ではない。**`ANSWERS.md` と frontmatter の `answer: B` は上のキュー原文のラベル体系**（本文と同じ並び）に合わせてある。

- A: 1 つの書式に統一する（却下 — 既存テストが assert している文字列を書き換えることになり、#674 の安全性の根拠そのものを失う。#674 が「挙動変更ゼロ」を主張できているのは**テストを 1 行も変えずに緑になる**からで、テストを書き換えた瞬間その証明が消える。畳み込みの効果は半分になるが、証明可能な安全性のほうを取る）
- B: **エラー文字列の書式は 3 種類のまま揃えず、重複している判定処理だけをまとめる**（**採用** — ユーザー回答 2026-08-12）。ユーザーに見える変化はゼロに保つ。PR #747 がジョイン・ロックに採った「ラベルを引数で渡す」やり方をそのまま延長する

## 却下案が復活する条件

エラー文字列を assert しているテストが、文字列ではなく構造（エラー型・コード）で判定する形に置き換わったとき。そのときは書式統一がテストの書き換えを伴わなくなるので、あらためて検討できる。
