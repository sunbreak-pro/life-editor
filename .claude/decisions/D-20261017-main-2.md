# D-20261017-main-2: refactor-core の申し送りへの回答（record_views の主キー・extension_apps の漏れ・tracker 枝の連番）

## 背景

キュー原文なし。2026-10-17 に、refactor-core が `.claude/comm/outbox/chat-refactor-core.md` に書いた申し送りを、こうだいさんが選択式の質問で答えた。回答は 3 問すべて推奨どおり。

申し送りの要点は 3 つ。

- #2260 の `record_views` は、Issue の主キー `(user_id, kind, unit)` だと、Realtime の削除の通知に、その人の uuid と記録の種類が全購読者へ届く。Supabase の Realtime は、削除の通知に RLS をかけず、主キーの値を付けて送る。そのため #2268 は、乱数の `id` を主キーにして `(user_id, kind, unit)` を UNIQUE にしていた。
- 0039 の `extension_apps` は、主キーが `(user_id, slug)` のまま Realtime の配信に入っている。同じ漏れがある。
- 2026-08-16 の申し送り（未回答だった）: tracker 枝は `chore/tracker-<chat>-YYYYMMDD` だが、squash merge した枝が残り、同じ日に 2 本目以降を同名で作り直せない。

## 選択肢と裁定

### Q1 record_views の主キー

- 乱数の `id` を主キーにし、`(user_id, kind, unit)` を UNIQUE にする（**採用** — 2026-10-17 の回答 / 削除の通知に uuid が乗らず、Realtime での別端末への反映も残る）
- Issue どおり `(user_id, kind, unit)` を主キーに戻す（却下 — 削除のたびに uuid と種類が全購読者に届く）
- Issue の主キーのまま Realtime から外す（却下 — 漏れないが、別端末への反映が再読み込みのときだけになり、計画書の Realtime の受け入れ条件を変えることになる）

### Q2 extension_apps の同じ漏れ

- Issue を起票して直す。順番は通常（**採用** — 2026-10-17 の回答 / #2271。着手は #2260 の push と merge のあと）
- 起票して、記録の計画より先に直す（却下 — 主キーの付け替えと、書き出しの並びや更新のキーの見直しが、記録の計画と同じ時期に重なる）
- 起票しない（却下 — 台帳の削除のたびに uuid と slug が届きうる）

### Q3 tracker 枝の連番

- 規約に、同じ日の 2 本目以降は `-2`、`-3` を付けると書く（**採用** — 2026-10-17 の回答 / `worktree-policy` スキルに追記）
- merge 済みの枝をローカルで削除する手順を足す（却下 — 消し忘れが残るたびに同じ問題が出る）
- 対応しない（却下 — レーンごとに付け方が割れる）

## 波及

- 計画書 `2026-10-12-records-aggregation-views.md` の設定表の図を、`id` 主キー + UNIQUE に直した。
- `.claude/skills/worktree-policy/SKILL.md` に、tracker 枝の連番の規約を足した。
- #2260 は PR #2268 の実装のまま進める。Issue 本文の主キーの記述は、この D ファイルが上書きする。
- 記録の docs の追随（#2265）で、`db-conventions.md` の独立テーブルの規約に `record_views` を足すときは、主キーを `id`、UNIQUE を `(user_id, kind, unit)` と書く。
