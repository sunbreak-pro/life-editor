# D-20260920-main-1: パスワード付き Note の保護をどこまでやるか

## 背景

#1763。現在の「パスワード」は画面のぼかしだけで、本文は MCP から素通しで読める（`mcp-server/src/handlers/noteHandlers.ts:57` の SELECT に `has_password` が無い）。ロック済み本文は DOM にも配信済み（`shared/src/components/materials/LockedBodyGate.tsx:26` が「これは security ではない」と明言）。

MCP はオーナー本人として `signInWithPassword` するため（`mcp-server/src/supabase.ts:92`）、RLS owner-only は防御にならない。Remote MCP の認可境界は URL パスの共有シークレット 1 本（`mcp-server/src/worker.ts:38`）。

## 選択肢と裁定

- **A: サーバ側フィルタ（採用 — 2026-09-20 ユーザー裁定）**: MCP と shared の読み取り経路が `has_password` を見て、ロック済み Note の本文を返さない。DB には平文が残るため、DB バックアップとオーナーの JWT からは読める。実装が小さく、解錠 UX も検索も壊さない
- B: パスワード由来の鍵でクライアント側暗号化（却下）: DB にも平文が残らないが、パスワードを忘れたら復旧不可になり、`search_all` と Briefing が本文を引けなくなる。代償が大きいため今回は採らない

## 波及

A が守るのは「Claude / MCP / 誤った共有からの閲覧」であって、「DB バックアップ・オーナートークンからの閲覧」ではない。したがって **Note に書いてよいのは「他人に見せたくないメモ」までで、本番の資格情報の保管庫としては使えない**。この限界は #1763 の本文に明記する。

B を将来必要と判断した場合は、本決定を supersede する新しい D ファイルを作る。

## 関連

`docs/known-issues/027` の「平文保存」部分は #118（PBKDF2-HMAC-SHA256）で解消済み。本決定はその後継論点（本文そのものの保護）を扱う。
