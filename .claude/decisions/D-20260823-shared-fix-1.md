# D-20260823-shared-fix-1: known-issue に「入口を張れない」知見をどう扱うか

## 背景

（#1087 の「決めてもらう必要があるもの」①。回答は同期で得た）

`docs/known-issues/` に書いても、実際に引かれるのは常時ロードされる場所（CLAUDE.md / `rules/` / `memory/`）から ID で指されている少数だけで、ディレクトリに置いただけのものはほぼ死蔵している。

- #1086 の計測（`scripts/known-issue-usage.mjs`・630 トランスクリプト / 240 targeted セッション）で、**30 本中 5 本が参照 0**（007 / 010 / 023 / 030 / 032）
- 最多の 031（56 回）と 027（27 回）も**自発参照ではなく**、`CLAUDE.md:68` と `memory/chat-main.md` からの注入で視界に入っているだけ
- 逆に、参照されても外すことがある。PR #1083 で題名の一致した 023 を読んだが、書かれていた原因は無関係で、真因は `npx` のプロンプトが stdout に混ざったことだった（**参照 0 のまま初めて引かれ、そして誤誘導した**）
- 今の採否条件は「再発しうる障害知見か」だけを見ており、**入口が張られるかを問うていない**

## 選択肢と裁定

- **C: 入口を張れないなら、先に `rules/` へ 1 行足してから書く**（**採用** — ユーザー回答 2026-08-23）。採用条件は「常時ロード面から ID 参照を張れること」。足せない（＝そこまでの価値がない）知見は書かない。理由: 実測で参照されている 3 本（031 / 027 / 026）はすべて常時ロード面から指されており、入口の有無が参照の有無とそのまま一致していた
- A: そもそも書かない（却下 — 一番厳しいが、「入口を作れば生きる知見」まで捨てる）
- B: plan / PR 本文の Worklog に留める（却下 — ディレクトリは増えないが、次に踏んだ人が辿る経路が「過去 PR の全文検索」しか無くなる。入口の無さは同じ）

## 却下案が復活する条件

- `rules/` 側の 1 行が積み上がって常時ロードのコストが問題になったとき → B（Worklog 止まり）を既定に戻し、`rules/` への昇格は再発 2 回目からにする

## 波及

- `rules/records.md` §2 が採否条件の正本。`docs-workflow` スキルは条件を**書き写さず参照**する（#1087 の DoD）
