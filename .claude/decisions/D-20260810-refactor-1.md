# D-20260810-refactor-1: ルーチンの Undo/Redo を繋ぐか、コードを消すか

## 背景

2026-08-10 のリファクタ調査で判明。`RoutineProvider` だけが UndoRedo に接続されていない（`ScheduleItemsContext` / `DailiesUnifiedContext` / `NotesUnifiedContext` には `useUndoRedoOptional()` の自動接続がある）。そのため `useRoutinesAPI` の undo/redo 用コード約 60 行は**実行されても何も起きない空撃ち**になっている。加えて `createNoopUndoRedo()` をレンダー本文で毎回呼ぶため、RoutineContext の値が毎レンダー変わっている。

Issue #672（use\*API の load effect 共通化）で同じファイル群を触るが、「ルーチンの Ctrl+Z を機能として出すか」は挙動の追加なので P-008 に従い実装せずキューへ積んだ。

## 選択肢と裁定

- **A: 繋ぐ + i18n ラベルを 3 件足す**（**採用** — ユーザー回答 2026-08-11）。`useUndoRedoOptional()` を `RoutineContext` にも配線し、`undoRedo.labels` に `createRoutine` / `updateRoutine` / `deleteRoutine` を en・ja 両方へ追加する
  - 利点: 既に書かれている約 60 行が機能する。他 4 ドメインと挙動が揃う（ルーチンの作成・更新・削除を Ctrl+Z で戻せる）
  - 代償: 挙動の追加なので #672 の「挙動変更ゼロ」原則から外れる。繰り返し系の undo は生成済み Event との整合確認が要り、実ブラウザ検証が必須になる
  - **i18n ラベルの追加は必須**: 繋いだだけだと `en.json` / `ja.json` に routine 系のラベルが無く、`UndoRedoHost` の defaultValue フォールバックで「Undid: createRoutine」という生キーの toast が出る
- B: 空撃ちコードを消す（却下 — 後で欲しくなったら書き直しになる。既に書かれている実装を捨てる判断は、機能として要らないと確定してからでよい）
- C: 現状維持・コメントで「未接続」と明記（却下 — 空撃ちコードが残り続け、読む人が「なぜ効かないのか」で毎回悩む）

## 却下案が復活する条件

ルーチンの undo が実装してみて Event 生成との整合を保てないと判明した場合（繰り返し系の undo が生成済み Event を孤児にする等）は、B（削除）へ倒す。その場合は新しい D を作って supersede 連鎖で表現する。

- Issue #672 の「判断待ち」節を裁定済みへ更新。**挙動変更ゼロの例外**として本裁定 ID を明記
