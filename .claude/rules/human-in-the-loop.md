# 人が差分を説明できる状態を保つ（Human-in-the-Loop）

> 2026-11-09 こうだいさんの指示（Gemini 案の 4 原則を取り込む）。根拠と穴の分析 = [`docs/reports/2026-11-09-agent-governance-and-harness-map.md`](../docs/reports/2026-11-09-agent-governance-and-harness-map.md)。「ユーザーは見ていない」前提（グローバル CLAUDE.md 前提 1）はそのままで、止まって待つのではなく、決まった場所に書いて残すことで、こうだいさんがあとから差分を読んで人に説明できる状態を保ちます。待つのは既存の 👀 / 🛑 Gate だけです（中ティアで待つかどうかはキュー D-20261109-harness-1）。

対象は `lead-pipeline` の中・重ティアです。軽ティア（typo・文言・1 ファイルの自明な直し）と、画面もコードも変えない docs だけの変更は対象外です。

1. **仕組みの仮説を先に書く**。着手時のスコープ宣言（触るファイル / 完了条件 / 触らないもの）に「どういう仕組み・順序で動く想定か」を 1〜3 行足します。重ティアは計画書の Context に書きます。実装が仮説と違ったら、PR 本文の「仮説と実際」に何が違ったかを書きます。
2. **テストが通ったことを完了の理由にしない**。PR 本文（PR を出さないときは最終報告）に「確かめたこと」と「確かめていないこと」を分けて書きます。確かめていないことには、SKIP したゲート・jsdom で見えない座標依存の経路・実ブラウザ待ち・db push 前の DDL を入れ、誰がいつ確かめるかを添えます。
3. **読む順を書く**。差分が 3 ファイルを超えるか、仕組みが一読で追えないときは、PR 本文に「読む順」（最初に開くファイル、処理の流れ、仕掛けのある場所）を書きます。目標は、こうだいさんが差分を読んで人に説明できることです。
4. **確認の問いを 1〜3 つ置く**。重ティアと、中ティアのうち仕組みが自明でない変更では、PR 本文か最終報告の末尾に、読み手が答えられるべき問いを置きます（答えは折りたたみに入れます）。理解のずれを見つけるためのもので、問いのための問いは作りません。

- PR 本文の骨組みは `.github/pull_request_template.md` です。`gh pr create --body-file` で本文を渡す issue-workflow の PR には効かないので、`.claude/issue-workflow.md` §PR の決まりに同じ項目を足すまでは対象外です。
- これらは宣言で、機械の実体はありません。実体の候補は報告書 §4 にあります。
